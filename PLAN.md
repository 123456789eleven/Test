# Custodian — Kelly Benefits architecture

This file is the durable reference for how the Kelly Benefits section of Custodian is organized, kept up to date as that shape changes. Custodian's other sections (Overview, Insights, Landscape, Study) are unaffected by everything below.

## React + Vite (2026-08-24, `react-migration` branch — not yet merged to `main`)

The whole app moved off static vanilla HTML/JS onto React + Vite, built on a `react-migration` branch rather than directly on `main` — this replaces a live site's entire delivery mechanism, and `main` stays the safe, working rollback point until a separate, explicit merge decision. Everything below describes the *old* `js/`-file architecture; once this branch merges, those references become historical (kept as-is rather than rewritten preemptively, since the merge hasn't happened yet).

**Stack**: React 19 + Vite 8, plain JS/JSX (no TypeScript — an explicit assumption, not asked about, since it's reversible later), `react-router-dom` v7 via `HashRouter` (not `BrowserRouter` — GitHub Pages has no server rewrite rule, and hash routing avoids the deep-link-404-on-refresh problem entirely), `@tanstack/react-query` for all Supabase reads/writes (replacing the old hand-threaded `onSaved` refetch-callback pattern with `useQuery`/`useMutation` + `invalidateQueries`), `@react-three/fiber` + `@react-three/drei` for the Hologram scene (declarative scene graph + `useFrame`, not raw Three.js imperatively driven from a `useEffect`).

**Structure**: `src/views/*.jsx` (one per route, mirrors the old `js/views/*.js` naming), `src/components/` (shared + per-feature: `shell/` for the app chrome, `charts/` for the two shared chart primitives, `hologram/` and `orgedit/` for the scene's supporting pieces), `src/hooks/` (`useAuth`, `useSearchRegister`), `src/lib/` (`supabaseClient`, `searchIndex`), `src/styles/` (design tokens + component CSS, one global stylesheet chain imported once from `main.jsx`, same philosophy as the old single-`<style>`-block approach — just split into real files instead of 860 inline lines). `data/*.json`/`study/`/`favicon.svg` moved under `public/`. `.github/workflows/deploy.yml` builds and deploys via GitHub Actions (triggers on push to `main` — won't fire on this branch); **the repo's Settings → Pages source still needs to be switched from "branch" to "GitHub Actions" once this merges** — that's a one-click setting only the user can flip, not something committable.

**Design-system cleanup done during the port, not deferred**: the two unrelated token systems that were both named "Aurora" now have distinct names (global tokens keep it; the homepage-only palette is `--ov-*`, "Overview hero palette"). `.integration-box`/`.crosscutting-box` (identical component, two names) merged into one `<Callout>` component / `.callout-box` CSS class (old names kept as aliases). `.hbar-*`/`.co-hbar-*` (same bar-chart pattern, two prefixes) merged onto one `<BarChart>` component / `.hbar-*` class. The org-edit modal's split `.oe-*`/`.orgedit-*` naming unified onto `.oe-*`. `insights.js`'s and `landscape.js`'s two independent hand-rolled "SVG line + hover tooltip" implementations became one shared `<SparklineChart>`. The embedded base64 `@font-face` became a real `.woff` asset file.

**What did NOT get carried forward, on purpose**: `js/migrate.js` (one-way localStorage→Supabase migration for pre-Supabase users) — no React equivalent exists; flagged as an assumption during planning rather than silently dropped, since a user who never signed in and still has real unmigrated localStorage notes would lose that path. `js/orgmap.js` and `js/connectionmap.js`'s actual `renderConnectionMap` function were already dead code before the migration (zero callers) and didn't get ported; only `connectionmap.js`'s pure `findVerticalOf` helper survived, now inlined into `src/components/hologram/orgTree.js`.

**A real bug caught during the Hologram port**: the old scene's `expand()` silently no-ops on a node with zero children (an empty division, a freshly-added department with no functions yet) rather than flipping accordion state. The first React draft missed this guard; caught and fixed against the original before landing (`src/views/Hologram.jsx`'s `hasChildren()` check in `handleClick`).

**Explicitly out of scope for this pass, same as before the migration**: the animated-workflow-simulation feature (a traveling pulse through a real workflow's steps) — still real future work, still blocked on the same data-linkage gap (most `workflow_steps` don't link to a real org node), not something this migration built toward or scaffolded for.

**Bundle size**: Three.js + `@react-three/fiber` + `@react-three/drei` are the large majority of the app's JS weight and only the Hologram route needs them — `App.jsx` lazy-loads that route (`React.lazy` + `Suspense`), so the rest of the app's initial bundle is ~518KB instead of ~1.47MB, with Hologram's dependencies in their own ~952KB chunk loaded only when that page is actually visited.

**Verification ceiling, same limitation as every other visual change this session**: `npm run build` succeeding and the built `dist/` serving correctly under the `/Test/` base path (including the standalone `public/study/` app) are real, checkable signals that didn't exist for the old static-HTML app — but actual rendering/interaction (does the 3D scene look right, do the CRUD forms work, does click-vs-drag-orbit behave) still needs a real browser and real eyes, which this session doesn't have. Not yet confirmed working end-to-end by a human.

## Two pages — Hologram (full-screen structure) + Company (narrative)

Kelly Benefits split back into **two pages** (2026-08-21, see History) after the single-page version was judged not to "display cleanly": too much narrative content (hero, SWOT, leadership, history, COBRA process, division-flow) bolted around the one thing that actually needed room to breathe — the 3D scene. The split is by *kind of content*, not by structure-vs-relationships (that unification from the earlier merge stands):

- **`#/hologram`** (`js/views/hologram.js`) — full-viewport, minimal-chrome. Registered via `Router.register("hologram", renderHologramView, { fullscreen: true })`; the `{ fullscreen: true }` option is a general router feature (see below), not hologram-specific. Holds only the 3D scene itself (legend/canvas/label/detail panel) plus a one-line header linking to `#/company`. No hero, no SWOT, no leadership list, no COBRA card — just the live structure.
- **`#/company`** (`js/views/company.js`) — normal chrome, like Overview/Insights/Landscape. Holds everything relocated out of Hologram: hero stats, "Where I fit," company snapshot, integration notes, the division-flow client-journey card, the COBRA process card, crosscutting-concerns box, SWOT, leadership list, company history. Has its own small Supabase fetch for `org_divisions`/`org_people` (same "each page owns its data query" convention as every other view) rather than sharing state with Hologram.

**Router gained real fullscreen + teardown support** (`js/router.js`): `Router.register(path, renderFn, options)` now accepts `{ fullscreen: true }`, toggling `body.route-fullscreen` (CSS in `index.html` collapses the sidebar/topbar to a slide-in drawer + floating translucent bar, reusing the existing mobile off-canvas drawer mechanism rather than inventing a second nav paradigm). More importantly, `navigate()` now calls a stored cleanup function (whatever the previous route's render function returned) before swapping `#viewMount`'s content. **This fixed a real, pre-existing leak**: `hologram.js`'s Three.js `animate()` render loop and `resize` listener were never torn down on navigation before this — every visit left an orphaned `requestAnimationFrame` loop running full WebGL+bloom rendering in the background. `buildScene()` now returns `{ rebuild, dispose }`; `dispose()` cancels the loop, removes the listener, and disposes the renderer/controls. Every view that returns a cleanup function from its render call benefits from this, not just Hologram.

**Phase 2, not yet built**: the ask that prompted this split was really "make the scene actually simulate workflows" — an animated traveling pulse moving through a real workflow's steps, branching at real decision points. Two research passes confirmed this needs its own, separate effort: (1) a real animation engine (nothing in the codebase does clock-based motion along a path yet — `rebuildLines()`'s `QuadraticBezierCurve3` curves are baked to static points once, never re-sampled per frame), and (2) real data linkage (only 22 of COBRA's 56 `workflow_steps` currently link to any `org_function` via `task_id`, and those 22 collapse onto just 2 of 75 functions; 34 steps have no link at all, and several name external parties — the client, the carrier, the qualified beneficiary — that don't exist as nodes anywhere in the schema). Confirmed approach for when this is built: add honest, clearly-labeled external nodes for real actors named in the source rather than forcing them into `org_functions`/`org_people`, backfill real function links where a single answer is unambiguous, and leave genuinely ambiguous steps unlinked rather than guessed. **Don't mistake the current static scene for this being done** — it isn't, yet.

## One WebGL scene, not an org chart

Structure and relationships live in one real WebGL 3D scene (unchanged from the earlier merge, just now on its own full-screen page):

- **Hierarchy** reads through node depth/size — divisions are the largest nodes, departments mid-sized, job functions smallest, all the same shared shape (a scaled octahedron), positioned deterministically (trig math, no physics/force-directed layout — this project's standing preference).
- **Relationships** read through glowing lines between nodes, driven by real `org_connections` data only. A connection always resolves to whatever tier is currently expanded for each endpoint (function if drilled in, else its department, else its division) — see `resolveVisible()`/`rebuildLines()` in `js/views/hologram.js`. Currently only Advantage has any modeled connections; the other three divisions render visibly dim/quiet rather than having fabricated edges added to look more populated.
- Progressive disclosure (click a division to reveal its departments, click a department to reveal its functions) with accordion behavior — expanding a new branch closes whichever one was open before it at that level, so the scene never accumulates every branch anyone has ever clicked.
- Corporate Functions is a fifth peer node built from real `org_people` rows (`parent = 'root'`), with its real people as the node tier beneath it (no fabricated department structure — it doesn't have one).
- Everything that isn't the scene itself — Where I Fit, SWOT, division-to-division client flow, the COBRA process card, company snapshot/leadership/history — lives on the separate `#/company` page now (see the Two Pages section above), not bolted around the canvas.

Editing (add/edit/delete for divisions, departments, functions, people, connections) happens via hover on a node in the 3D scene — an "Edit" and/or "+ Add" button appears in the floating label, wired to the existing `js/orgedit.js` modal. Divisions are edit-only (no add/delete — matches `orgedit.js`'s own rule, since the four divisions are fixed).

**Client Outcome** is deliberately not a node in the scene — no real client-quality/outcome data exists anywhere in this system to trace toward. It stays a documented absence (with an explanatory caption on the page), not a fabricated metric.

## Data model

**Org structure** (unchanged): `org_divisions`, `org_verticals`, `org_functions`, `org_people`, `org_connections` — 5 tables from the "Foundation" work, public read / sign-in-gated write.

**Workflow/tooling/hierarchy/stakeholder layer** (additive, from the "Schema Extension" work): `org_titles` (rank reference — now populated, see "Org Roster" below), `org_people.title_id` (nullable FK to `org_titles`), `org_people.manager_id` (nullable self-referencing FK to `org_people` — the real direct-manager reporting line, distinct from `parent`, which is division membership, not a reporting line), `tasks`/`tools`/`task_tools` (function-level capability layer — deliberately function-level not person-level, matching how `org_connections` already works), `workflows`/`workflow_steps`/`workflow_transitions` (a generalized version of what `js/cobraprocess.js` already does for COBRA specifically — real branching via `workflow_transitions`, not a forced straight line), `external_stakeholders`/`workflow_stakeholders` (the first place this project represents anything outside Kelly Benefits itself). This layer does not touch `org_connections` or the hologram's rendering — it's a separate, additive layer that could eventually be visualized alongside the 3D scene, not a replacement for anything above.

**Org Roster** (2026-08-20) — `org_titles` was populated with a real 8-rank ladder (Chairman/Chief/EVP/SVP/VP/Director/Manager/Individual Contributor) derived from real title conventions, and `org_people` grew from 20 rows to 464 via a real Kelly Benefits org-chart export the user supplied (`fs.pdf`/`fs.txt` in scratchpad) plus the public Senior Leadership Team/Our Team roster (`team-bios.txt`), both reconciled against the live table rather than duplicated. Every person has a real `title`/`title_id`; 442 of 464 have a real `manager_id` reconstructed from the chart's header-badge-count structure — the remaining 22 are left `null` rather than guessed, because the export doesn't show their own parent link (a handful of subtree roots, like the Advantage/Payroll Operations & Growth Leaders, whose own manager wasn't visible in this particular export). `js/views/hologram.js`'s Corporate Functions tier renders every `parent="root"` person as an individual 3D node, and this import pushed that count from 7 to roughly 130 (most of Finance/HR/Marketing/Compliance/IT is genuinely `root`-parented — none of the 4 real divisions). No code change was needed for this (the existing wedge-spacing logic already divides by however many children exist), but it's a real, visible change to the scene, not a bug, if a future session sees a denser Corporate Functions tier than described earlier in this file.

Two things flagged for the user to confirm in real life, not auto-resolved: (1) a chart node "Robert Pfeifer, Growth Leader KBP" may be the same real person as the already-live "Brian Pfeifer, Growth Leader, Kelly Benefits Payroll" — kept as two separate rows since the first names genuinely differ; (2) a chart node "John Kelly, VP of Retirement Advisory Services" may be the same real person as the already-live "John Kelly Jr." (whose bio-page title, "SVP, Growth," doesn't obviously match) — also kept separate. A third, similar case — "Mary Backer-Miceli, VP of Human Resources" vs. the already-live "Trish Backer-Miceli, VP, Human Resources" — was resolved (not just flagged) during verification: the identical specific title at one company was decisive enough to treat as the same person, so that one was merged into the existing `trish` row rather than left duplicated.

`js/orgedit.js`'s person add/edit form does not yet expose `title_id` or `manager_id` in its UI — the data layer is real now, surfacing it in the edit modal is a separate future decision, same pattern already used for `tasks`/`tools`.

**COBRA's real process is migrated into this layer**: the existing, real, sourced `data/cobra-process.json` became the first real `workflows` row (plus its `workflow_steps`/`workflow_transitions`/relevant `tasks`/one real `tool` — KTBSonline, named explicitly in the source — and real `external_stakeholders` — Client/Employer, Qualified Beneficiary, Insurance Carrier). **`js/cobraprocess.js`'s rendering was deliberately left untouched** — it still reads `data/cobra-process.json` directly, not the new tables. Migrating the data and rewriting the renderer to be schema-driven were treated as two separate decisions; only the former was done. Don't assume the COBRA process card on the Hologram page is reading from `workflows` — it isn't, yet.

## Database automation

Schema changes no longer go through manual copy-paste into the Supabase SQL Editor. The Supabase CLI is installed (`C:\Users\bearf\bin\supabase.exe`, on PATH) and linked to this project (ref `hbqrzbgvryfrbybenhyj`) via a personal access token stored at `C:\Users\bearf\.supabase-token` — deliberately outside this repo, not committed, not in any tracked file. Migrations live as versioned files in `supabase/migrations/` (the first, `20260821004409_remote_schema.sql`, is the pulled baseline of everything that existed before this workflow started; real changes are every file after that). Workflow for a new schema/data change: `supabase migration new <name>`, write the SQL, `supabase db push --dry-run` to preview, then `supabase db push` for real. Docker Desktop needs to be running for `db pull`/schema-diffing commands (not for `db push` itself) — it was installed and started as part of this setup.

## Editing / shared modules

`js/orgedit.js` is the single shared edit modal, used from the Hologram page's node-hover buttons. `js/orgmap.js` (the old tree renderer) was deleted (2026-08-21) — it had zero callers anywhere in the repo. `js/connectionmap.js` (the old 2D relational graph) still exists — its own `renderConnectionMap` is unused, but its `aggregateConnections`/`findVerticalOf` helpers are still imported by `js/views/hologram.js` via `window.OrgConnections` — don't delete it without checking that dependency first.
